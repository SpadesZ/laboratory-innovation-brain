## 3. The VS-SP-001 flow, end to end

§26.1: *intent-aware retrieval → competing hypotheses → capability/cost planning → Job → evidence →
belief event → failure/heuristic candidate.* Every arrow is an existing governed component; M4 adds
the planner, the loop that drives the arrows, and the pack's verification actions.

1. **Ingest.** `lab-brain episode open` (§25.4's CLI clause) opens a ResearchEpisode and ingests the
   project's files through M1's `IngestionService`: raw bytes stored and hashed before any parsing
   stage (UX-004), each file one IngestionItem whose state the inbox derives.
2. **Competing hypotheses.** M3's `StructuredDebate` — intent-aware SourcePolicy, the Critic's
   inverted retrieval, admission through §8's gate. Every rival is a certificate in a ROOT-CAUSE set
   with typed Predictions over the pack's diagnosis observables (one SUPPORTS and one CONTRADICTS
   prediction per check). The debate's critiques are what later let a REJECT pass §7.6.
3. **Plan.** `LeastCostPlanner` reads the admitted state of every rival, consults case memory
   (§6.9's FailureAnalyses with the same symptom — recorded on the plan, deciding nothing), asks
   whether the admitted evidence already licenses a move, and otherwise ranks the capabilities that
   produce a predicted observable. The plan is persisted (`011k`) whether or not it chooses.
4. **Job → Run.** The chosen capability's `VerificationWorkflow` (§24.3 `register_workflows`)
   dispatches a typed tool through `BudgetedToolDispatcher` (COST-001's gate, span, both ledger
   rows) against a durable Job; `CapabilityRoutedRunner` executes it through `run_simulation`, the
   one seam that mints a Run. The backend writes its raw output through `RunOutputSink` — scanned,
   content-addressed, stored and placed in the project **before** the Run exists.
5. **Evidence.** The workflow reads the Run's STORED output back by id and applies the pack's
   versioned rule. The loop builds Observation(run) → Attestation(run, OBSERVED/SIMULATED, the
   authority the Run earned) → the RelationJudgments the rivals' own predictions declared for that
   outcome, each carrying the ConditionMatch between the Run's conditions and the diagnosis's; the
   Attestation passes M1's `EvidenceAdmissionGate` (EVI-003, EVI-009).
6. **Belief event.** For each rival, every governed move whose `evaluate` on the admitted evidence
   is ALLOW is attempted through M3's `HypothesisBrain` — the EPI-001/SRC-002/§7.6 preconditions,
   then M1's `BeliefEpisode` (durable Decision, event, re-derivation). Coarse evidence challenges and
   cannot reject or confirm (SIM-002, via `auth:silicon_photonics@1.1.0`).
7. **Failure memory.** A SUPPORTED rival ends the loop; `trace_root_cause` + `confirm_root_cause`
   produce a CONFIRMED FailureAnalysis that `011l` accepts only if its evidence reaches a SUCCEEDED
   Run and stored Artifacts. Otherwise the analysis is OPEN (waiting on a person, a seat or a budget)
   or INCONCLUSIVE. Recurring confirmed failures of one class across ≥ 2 episodes become a
   PENDING_REVIEW CandidateHeuristic (HEU-001's approval is M7's).

## 4. Architectural decisions and the interpretations they rest on

**4.1 Full §9.1 lives in `verification/`, not in M0b's hard-locked `core/sufficiency.py`.** M0b
implements plausibility clauses 1–2 and hands `evaluate_hypothetical` the same view as the baseline,
so the authority the observation *would* carry never reached the authority gate. M4 asks exactly
§9.1's question with §17.5.1's `implied_authority_class`: the hypothetical view is the current view
plus the class the producing capability would yield, plus the ConditionMatch its planned execution
will have (computable before it runs — the loop runs it under the diagnosis conditions), plus one
independent work. Both calls are the canonical operator's two methods; nothing decides a transition.

**4.2 Every verification action is a Job with a Run, the local inspection included.** EPI-002's chain
is `... → Run → Artifact` and VS-SP-001's point is that the cheapest check often confirms. So the
solver-free design readers (`inspect_contact_connectivity`, `inspect_normalization_basis`) execute
through the same seam as the solves, recorded with their own validity schema
(`design_inspection_validity@1.0.0`: reader id/version, input project hash, rule). Their DESCRIPTORS
stay `inspect_*`: no capability, no seat. The one M2 docstring this made inaccurate —
`ToolRequest.job_binding` said every `inspect_*` request binds no Job — described a default, not a
rule the dispatcher enforces; its wording is corrected (documentation only) and the M4 requests
override it exactly as `run_*` requests do.

**4.3 DESIGN_INSPECTION is a new authority class in a new comparator version.** A reading of the
design is evidence about the designed device (SIM-002's family), ranks with a validation-fidelity
solve and is INCOMPARABLE with measurement (§10.6). `1.0.0` is unchanged and stays registered — every
M2 decision re-derives under it — and the vertical names `1.1.0` on its decisions.

**4.4 M2's SIM-002 policies are reused unchanged; M4 adds only ACTIVE→SUPPORTED.** Two versions of
one rule: designed-device evidence (rule SIM_STANDARD) and fabricated-device evidence (rule
MEAS_CALIBRATED), each requiring SUPPORTS, an EXACT/COMPATIBLE ConditionMatch and one independent
work. Target order is REJECT, PROMOTE, PROMOTE-MEASURED, CHALLENGE, so a standard-fidelity
contradiction rejects rather than stopping at a challenge.

**4.5 Independence of run-derived evidence is counted by execution.** §6.17's WORK basis, with the
Run as the work: two attestations read off one Run are one source. Evidence that reaches no Run
counts as unknown (EVI-004).

**4.6 Hypotheses come from the M3 debate; the catalog is a test double of the model.** The rivals'
mechanisms and predictions are what M3's deterministic `MockScientist` answers from the fixture's
catalog; no model is called. The debate is run at `minimum_hypotheses = 5` so the rival set is fixed
across benchmark cases.

**4.7 Precedents inform; they do not re-rank.** Case memory matches the normalised symptom exactly
and is recorded on every plan; the ranking is the SelectionPolicy's alone. A similarity model would
be a judgment the planner then leans on.

**4.8 The loop never forces a move and never chooses between contradicting evidence.** It evaluates
first and attempts only ALLOW moves; a precondition the reviser refuses is recorded, not retried; a
rival holding both SUPPORTS and CONTRADICTS evidence is left for a person.

**4.9 `register_workflows` is added to the DomainPack protocol; `declared_outcome_space` and
`disagreement_metric` are answered by the registries.** The base module had reserved all three for
M4. The space an action is read in is the one the rival's admitted Prediction is bound to (and the
pack declared); the metric is `DisagreementMetricRegistry.for_space`. A pack method returning the
same object would be a second source for one answer. ToyDomain registers a workflow (EXT-001).

**4.10 Benchmark isolation truncates; it does not roll back.** The stores and the seat broker run in
autocommit as production does, and the broker's refusal path does not survive inside a caller's
transaction. Each case starts from a reset database; the script refuses to run without
`--disposable`.

analyses; source artifacts exist; artifacts and locators required; append-only).

## 7. Adversarial cases tested

- a plan choosing an expensive action past a cheaper sufficient one — refused by the model and by
  `011k`; a ranking that drops a candidate; a foreign rationale; stopping while an action is
  sufficient; a single-dimension or `normalized_cost` policy; mutating a policy version or a plan;
- an invented outcome, an excluded one, one outside a validity bound, one the domain rule FAILs, one
  with no validator, one a capability cannot yield now, one from a capability the pack never
  declared as a producer, predictions bound to an undeclared space version;
- the LLM-only fixture: a model's reading as the only support — the reviser refuses
  (ADJUDICATED_BY_MODEL_OPINION), the trace refuses (NOT_SUPPORTED), `011l` refuses the analysis;
- a confirmation citing an INFERRED attestation, a literature attestation that did not confirm it,
  a nonexistent attestation, a cause nobody admitted; a candidate from an INCONCLUSIVE analysis, an
  ACTIVE candidate; UPDATE/DELETE on the failure memory;
- a non-converged solve (challenges, never confirms or rejects), a licence outage (the Job parks
  WAITING_RESOURCE, cheap checks still run), a closed probe station (INCONCLUSIVE, nothing
  confirmed), a request wrapping another capability's execution, a workflow for an undeclared
  capability or tool, an EXECUTED result with no Run, a run output carrying a credential (refused
  before storage), a promotion failure between the stores (compensated, never deleting rows an
  earlier identical emit wrote).

## 9. Remaining risks and deliberately deferred work

- **TST-001's licensed replay is not performed** (risk R-1): no Lumerical seat and no licensed
  provider exist here. The mock half runs in CI; the licensed test fails when enabled.
- **The backends are mocks.** The mesh and DC solvers are analytic stand-ins whose thresholds are
  decided by the device description; they prove the typed contract and the loop, not physics.
- **Hypotheses come from a deterministic mock model**, answering from a catalog written for this
  benchmark. The benchmark measures the verification loop, not hypothesis generation.
- **Each check tests one rival.** The catalog declares no cross-rival predictions, so M3's
  disagreement metric is not what separates candidates here; sufficiency is.
- **Case memory is exact-symptom matching** and does not re-rank. **The loop does not auto-escalate
  INCOMPARABLE authority to review** (EPI-004's path remains the governed transition's); it records
  refusals.
- **The benchmark runtime** is ~45 s on PostgreSQL; it runs in CI's backend job.
