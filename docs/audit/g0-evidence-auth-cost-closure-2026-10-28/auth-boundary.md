# 研究執行的身分驗證邊界（G0-A，migration `011q`）

日期：2026-10-28

## 問題

`011n` 讓每個 WEB_SESSION 研究執行都帶有一個 `session_audit_ref`。資料庫會檢查：
這個參照指向該執行者本人仍有效的工作階段，而且執行者是專案的有效成員。

但是工作階段參照不是秘密。任何能讀 `account_sessions` 或報告的人都能抄到它。
只要擁有應用程式角色權限，資料庫寫入者就能自己插入一筆 WEB_SESSION 執行，
寫上別人有效工作階段的參照，並用同一位執行者、同一個專案和合法的時間。
`011n` 會接受這筆資料。在 `011q` 之前，報告和頁面還會把它顯示成「已登入的網頁工作階段」。

測試 `tests/e2e/test_g0_interaction_attestation_postgres.py::test_a_forged_run_naming_a_real_session_is_never_shown_as_authenticated`
重現了這個情況。

## 做法

1. 網頁層收到已登入、且通過 CSRF 檢查的請求，並由它開始或接續研究執行時，會簽署一份標準化陳述。
2. 陳述綁定：研究執行、episode、追溯碼、執行者、專案、工作階段參照、路由、方法、
   `csrf_verified=true`、簽署時間、隨機 nonce，以及陳述種類和版本。
3. 簽章使用 Ed25519。私鑰只放在網頁層（環境變數 `LAB_BRAIN_INTERACTION_SIGNING_KEY` 指向的檔案）。
4. 公鑰釘選在資料庫之外（`LAB_BRAIN_INTERACTION_AUTHORITIES` 指向的檔案）。
   可以用 `until=` 讓舊金鑰退役，以便換鑰。
5. 陳述、簽章和金鑰識別碼與執行一起寫入，之後不能修改、補上或刪除。
6. 資料庫 CHECK 要求陳述的欄位等於這一列的欄位。所以把一份有效簽章搬到另一筆執行，會被拒絕。
   同一個 nonce 也只能用一次。
7. 資料庫不驗證簽章，也不應該由它驗證。驗證在 Python 端，用釘選的公鑰完成，
   而且每次顯示時都重新計算，不讀取任何已儲存的「已驗證」欄位。

## 主張等級

| 等級 | 意思 |
|---|---|
| `INTERACTION_VERIFIED` | 簽章能用釘選且在簽署時間仍有效的金鑰驗證，且陳述正好指向這一筆執行。只有這個等級可以說「源自經身分驗證的互動」。 |
| `SESSION_RECORDED_UNVERIFIED` | 有記錄工作階段參照，但沒有互動證明，或證明無法驗證（包括部署沒有釘選金鑰）。它不證明經過身分驗證的互動。 |
| `OPERATOR_UNATTESTED` | 操作者工作台或命令列。沒有主張任何登入。 |
| `LEGACY_UNATTESTED` | `011n` 之前的紀錄。沒有證明任何事項。 |

報告、匯出和頁面的中英文版本都會寫出等級。雙語一致性檢查（`AUTH_CLAIM`）會確認兩種語言寫的是同一個等級，
也會確認沒有任何一種語言在等級不是 `INTERACTION_VERIFIED` 時說「經身分驗證的互動」。

沒有設定簽署金鑰時，網頁仍可正常使用，執行仍會被記錄，但等級是 `SESSION_RECORDED_UNVERIFIED`。
也就是說：主張失敗時保守處理，但產品照常運作。

## 仍然存在的信任根

- 持有網頁層簽署私鑰的人，或能控制部署設定（釘選哪些公鑰）的人，可以讓陳述通過驗證。
- A12 仍然存在：擁有 migration 權限的資料庫寫入者可以直接改角色和狀態。
  這是操作者的信任根，屬於 Owner 的決定。本次修改沒有消除它，也不聲稱消除它。
- 把一份陳述重播到另一筆資料，會被資料庫拒絕；即使寫進去，也無法通過驗證。
- 如果有人偷了工作階段 cookie，並透過真正的網頁層操作，結果會是「已驗證的互動」。
  這是身分驗證的風險，不是來源紀錄的問題。

## 秘密

私鑰、工作階段 token 和 `session_hash` 都不會出現在資料庫、日誌、頁面或匯出中。
陳述只帶非秘密的 `session_audit_ref`。測試會在所有資料表和頁面中搜尋這些值。
