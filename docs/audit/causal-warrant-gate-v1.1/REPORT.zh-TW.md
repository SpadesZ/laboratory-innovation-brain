## 2. 審查者身分

【事實】
- 部署中所有程序都用同一組 PostgreSQL 超級使用者憑證，工作台沒有登入。所以資料列上寫著誰，本身不可信。為每個人建立資料庫角色也無效，因為超級使用者可以切換成任何角色。
- V1.1 改為：答覆是審查者以 Ed25519 私鑰簽署的陳述，簽署內容涵蓋答覆的每個欄位。
  - 公鑰由「審查權限者」（authority）登錄給特定專案中的特定人，登錄本身也有權限者的簽章。
  - 權限者的公鑰固定在**資料庫之外**的設定檔（`LAB_BRAIN_REVIEW_AUTHORITIES`）。
- 每次「計入答覆」的讀取都會驗證簽章：解析器的 `_counted`、儲存決策的 `verify`、重用前的 `confirmation_verifier`。驗證不過的答覆等於沒有答覆，既不認可也不否決。
- SQL（`012p`）在寫入時檢查外框：
  - 每筆新答覆都有登錄與簽章；
  - 登錄屬於回答者本人、在同一專案、未被撤銷；
  - 答覆時間晚於登錄與提問；
  - 舊的未簽章 `diagnostic_warrant_resolve` 已移除。
- 獨立授權：
  - 權限者不能登錄自己；
  - 一把金鑰只屬於一個人；
  - 權限者的金鑰不能當審查者金鑰；
  - 被撤銷的金鑰不能再登錄；
  - V1 的「跑 episode 的人與假說作者不能回答」維持不變。
- 撤銷從 `effective_at` 起生效。撤銷紀錄寫入後，SQL 不再接受該登錄的任何答覆；依賴已撤銷答覆的結論，重新檢查後不再被信任。
- 失效即關閉：
  - 沒有設定權限者時（預設範例檔），任何答覆都不成立；DOMAIN 依據照常計入，需要人的部分全部等待；
  - 012p 之前的未簽章答覆不計入（部署中沒有這類答覆）。

【解讀】未涵蓋的部分（記為殘餘風險，§9）：
- 持有權限者私鑰的人可以登錄任何人；控制部署設定的人可以選擇權限者。這是部署的信任根。
- 審查者可以誤用自己的金鑰（答覆可歸責，但不代表正確）。
- 跑 episode 的人的身分仍是自報的。
- 金鑰被竊、撤銷尚未寫入之前，可在 `effective_at` 留下的窗口內倒填時間。

## 3. 確認規則對每個寫入者

【事實】
- 確認規則的所有輸入都有紀錄：信念事件與決策、關聯、attestation、觀測、Run、答覆與登錄、衝突，以及（V1.1 起）已註冊的領域宣告。
- `confirmation_rule_breaches` 在資料庫中對紀錄評估迴圈的規則，逐條對應見設計記錄 §3.1。
- 觸發器 `failure_analyses_with_the_confirmation_rule_trg` 在規則不成立時拒絕 CONFIRMED 列；以下情況也會拒絕：
  - 漏列集合中的對手；
  - 引用的依據不是該原因支持的現行依據；
  - 宣告類別的成員沒有以類別正式名稱記錄。
- 宣告必須與程式碼一致（`SqlDeclarationSetStore.ensure`）：
  - 已存版本的摘要必須與程式碼相同；
  - 程式碼沒有宣告、卻觸及程式碼觀測量的任何宣告集（不論 set id），都會讓執行停止。
- 兩種寫法（Python 與 SQL）由差分檢查綁在一起：PostgreSQL 測試的 `CheckedLoop` 在**每次**迴圈執行後檢查，對每個成員，SQL 找不到違規當且僅當迴圈會確認它。涵蓋十個基準案例的兩種策略、V1 與 V1.1 的所有反例與對照，以及每次續跑。
- SQL 無法驗證 Ed25519。所以重用結論的讀取者（案例記憶、歸納器）只讀 `trusted_confirmations`，條件為：
  - 有依據；
  - 沒有標註；
  - 該原因的假說集合中每一筆答覆都驗證通過；
  - 每個 DOMAIN 依據都是程式碼宣告的類別。

## 4. 營運

【事實】
- `lab-brain admin review-queue <project> --declared-by <member>`：
  - 宣告新版本並停用舊版本；已排入的項目保留原期限；
  - 預設：容量 50、3 天到期、14 天逾期；
  - `declared-by` 必須是專案的在職成員；
  - 容器的 bootstrap 會為其專案宣告一個（`--if-absent`）。
- 每次 research run（新開或續跑）在驗證前，先以 OPS-002 的路徑清掃該專案逾期的審查；逾期的依據問題在同一次執行中重新詢問。
- `compose.yaml` 以唯讀方式掛載權限者設定檔；預設是不固定任何權限者的範例檔。

## 5. 已知錯誤確認的標註

【事實】
- `012p` 新增 `failure_analysis_flags`：只增不改，以內容摘要（`failure_analysis_digest`）綁定被標註的列。
- `flag_known_false_confirmations()` 只在下列欄位**完全相符**時寫入一筆 FALSE_CONFIRMATION 標註：
  - id、專案、episode、原因、失效類別；
  - 狀態為 CONFIRMED，且沒有依據引用。

  標註說明真因並引用稽核報告。沒有這筆列的部署不受影響；重跑不會再寫入。
- 結論本身不修改（測試確認摘要前後相同）。被標註的結論不被信任，不作為先例或歸納來源；episode 頁面在結論旁顯示標註。
- `lab-brain admin flag-analysis` 可記錄其他標註。
