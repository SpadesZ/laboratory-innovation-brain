## 2. 六項目標

### 2.1 專家識別碼形狀（目標 1）

- 【事實】`cognition/aliases.py`：每場辯論一張假說表（H）、一張證據表（E），依首次出現順序編號、只增不改；一個 canonical id 只對應一個代號；長得像代號的 canonical id 會被拒，因此沒有歧義。
- 【事實】專家、反方、涵蓋審查看到的一律是代號；反方原本在「否證條件」文字中仍會看到 `hyp:`／`prd:` 完整識別碼——自我測試發現後改為代號（`shown_falsifier`）。
- 【事實】解析（`roles.resolve_refs`）只接受「本次呼叫展示過的代號」或「完整的 canonical id」；前綴、改大小寫、未展示的代號、重複引用都拒絕。存下的 Position／CritiqueReport 一律是 canonical id；每次呼叫展示的對照表寫入 InferenceProvenance 的 `parameters.aliases`，可事後還原。
- 【事實】續跑不重新解析模型文字（`load_debate` 讀存下的 canonical 物件），因此不受影響；舊紀錄中的完整 UUID 仍可解析。
- 測試：長 UUID、首次 live 的 8 碼前綴原文、重複、畸形、對抗（未展示、他專案、改大小寫）、續跑：`tests/unit/test_g0_reliability.py`。

### 2.2 結構化輸出（目標 2）

- 【事實】每個角色呼叫送出該角色的 JSON schema（`response_format: json_schema`；只用 object／array／string／enum／required）。提供者以 400/422 **明確指名** response_format／schema 拒絕時，才不帶 schema 重送一次，並在推論來源記錄 `PROMPT_ONLY: HTTP 4xx`（只記狀態碼，不記對方原文）。金鑰錯誤、超長、5xx 等一律照舊報錯、不重送。
- 【事實】解析前唯一的修復：整段回覆只是一個 Markdown 程式碼區塊時取其內容，或去除位元組順序標記；兩者都記錄。JSON 內容一個字都不改、不補欄位。
- 【事實】解析器拒絕時，以同一角色再問一次（研究政策 `debate:research-run@1.1.0`，最多 2 次），附上解析器的拒絕原因；每次都是獨立、經預算閘門、持久記錄的推論（`attempt`、`retry_of`）。被拒回覆的內容不進入任何型別化物件；最後仍被拒就整步失敗並列出每次原因。
- 【事實】清單欄位：`null` 視為空，其餘非清單（`""`、`0`、`false`）一律拒絕。
- 【事實】提供者回報的 token 數（prompt／completion／total）寫入 LLM_CALL span，研究報告逐模型列出。
- 【事實】驗證 schema 傳輸的範圍：本機 Ollama 接受（qwen2.5:7b 實測，見 §5）；替身伺服器測試回退路徑。Gemini 是否接受這些 schema **未實測**（需計費呼叫）；若拒絕，會依上述規則回退並記錄。
  - 【勘誤 2026-10-27】上句寫於 Gemini 重測之前，已過時：§5.1 的擁有者授權重測中，Gemini 3.1 Pro 的 26 次回覆**全部在 JSON schema 模式下被接受**（0 次 400/422 回退、0 次重問、0 次修復；證據 `evidence/live_gemini_g0/*.provenance.json` 的 `parameters` 輸出模式欄）。仍未實測的是：其他 Gemini 版本、其他 schema 形狀，以及 Gemini 在拒絕時的實際錯誤格式。

### 2.3 假說涵蓋與驗證缺口（目標 3）

- 【事實】`cognition/coverage.py`：一個 observable 若同時符合以下三點，就列為「未涵蓋的低成本檢查」：
  - 在領域的預測詞彙中；
  - 這裡就能執行，且估計成本不需人員、金錢、授權席位，也不是不可逆；
  - 已准入的假說中沒有任何一個對它做 SUPPORTS 或 CONTRADICTS 預測。
- 【事實】輸入只有「假說、詞彙、能力描述、輸入種類」，**不讀裝置內容、基準答案或目錄**；測試證明不同裝置、不同真因的案例得到完全相同的待審清單（`test_the_unaddressed_checks_depend_on_...`、e2e 中三種裝置逐字相同）。
- 【事實】假說引擎就每一項只被問一次（`prm:hypothesis-coverage-review@1.0.0`）：要嘛新增一個**有證據依據**（必須引用展示過的證據）且機制不同的對立假說，要嘛**附理由婉拒**。提示明言「檢查便宜不是任何機制的證據」。新假說經 §8 准入，依據只取它引用的證據。
- 【事實】審查失敗或預算不足時，Stage A 的假說照舊，紀錄寫明哪些檢查仍未涵蓋；頁面「為什麼不能下結論」會列出仍無任何假說預測其結果的低成本檢查（會即時排除後來回合已涵蓋的）。
- 【事實】只新增、不刪除假說；最便宜原則不變（規劃器未改）。
- 【事實】回放：先前第二輪「不足證據」被外層區塊擋下的那次回覆，**其實已含「接點不連續」假說**；修復外層後可被接受（`evidence/baseline_four_real_runs.json` 的 `replay`）。其餘三次可解析的回覆都沒有涵蓋接點連通性。

## 7. 剩餘 G0 阻礙

1. **真實模型仍找不到接點開路的真因**（§5.1）：模型依證據婉拒、系統依設計不做沒人預測的檢查。可選方向（需擁有者決定，本輪未做）：
   - (a) 低成本、無副作用的檢查在沒有假說預測時也先執行為「篩檢觀察」，結果不改變任何信念，但若出現異常就觸發新一輪假說（須處理「事後才提假說」的風險：該觀察不得作為該假說的支持）；
   - (b) 把裝置檔的結構摘要（不含判定）作為證據提供給假說引擎；
   - (c) 維持現狀，接受「證據沒暗示就不檢查」。
2. 本機 7B 模型仍無法擔任主要推理（ROLE_HYPOTHESIS）。
3. 模型自寫的機制，即使觀察相符，也一定要人員回答診斷依據才會改變信念——這是 Causal Warrant Gate 的設計；G0 要得到「確認」，需要人員審查流程或擁有者決定的機制對應設計。
4. 模型文字不翻譯（§2.6）；策展中文尚待領域專家審閱。
5. ~~Gemini 對這些 JSON schema 的接受度未實測；拒絕時會回退並記錄。~~【勘誤 2026-10-27】已由 §5.1 實測：26/26 次在 JSON schema 模式下被接受；此項不再是阻礙。
6. 涵蓋審查的依據是引用、不是內容驗證；涵蓋與重問可能在預算偏緊時排擠反方。
7. 既有突變存活 `workspace_episode_ignores_membership`（基準即存在）與一條順序相依的結果——候選，未在本輪處理。
