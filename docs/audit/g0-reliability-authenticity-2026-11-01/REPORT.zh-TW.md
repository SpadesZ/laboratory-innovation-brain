## 2. 本機代理的成本風險(011v)

先證明漏洞(`evidence/local_proxy_before.log`:14 個測試中 10 個在 58c68be 失敗):
- 沒有設定預算時,送到本機的請求**不計量**。本機的 LiteLLM 代理可以把它轉給付費服務。
- 免費宣告可以寫 `*`:代理依模型名稱轉送,所以 `*` 會讓所有模型都免費。
- 「免費」的端點回答時帶著付費服務的計費標頭,沒有人發現。

修正:
- 本機請求和遠端一樣:要預留預算,或 Owner 宣告「這個端點的這個模型」免費。沒有 guard → 送出前拒絕。
- `LAB_BRAIN_LLM_SPEND_METER_LOCAL` 不再讀取。沒有開關能關掉本機計量。
- 免費宣告只能寫一個模型;舊的 `*` 紀錄不再算數。
- 免費端點的回答帶計費標頭或用量裡有費用 → 回報並拒絕這次呼叫;那筆宣告失效,直到 Owner 重新宣告。
  回報只存訊號名稱,不存數值;只能新增,不能改或刪。

剩下的風險:會刪掉所有計費痕跡的代理,和真正的本機模型分不出來。Owner 的宣告是信任根(SPEC-ISSUE-017)。

## 3. 人工授權的真實性(011w)

先證明漏洞(`evidence/unsigned_authorization_before_011w.log`):在沒有 011w 的資料庫,
服務角色可以用真實成員的名字寫入一筆**沒有簽章**的驗證授權,而且被接受。

修正(沿用 Causal Warrant Gate 的設計,但用自己的資料表,沒有改 warrant gate):
- review authority 為某人登記「授權金鑰」(Ed25519,scope `VERIFICATION_AUTHORIZATION`)。authority 的公鑰放在資料庫外。
- 授權是本人對全部欄位的簽章(假說、預測、capability、宣告雜湊、人、理由、時間、登記)。
- SQL 檢查外框:有簽章、是那個人的未撤銷登記、在登記之後、在假說之後、不在未來;規則 (l) 在採用證據時再檢查一次。
- Python 在每次讀取時驗簽(證據 sink、評估收集器的 `unverified_authorization`、scorer 2.3.0)。
- **不放寬證據採用**:011s 的每一條規則都還在;簽章是多加的一個條件。合法路徑(登記的人簽章)仍然可以支持篩檢後假說。

攻擊測試:未簽章、別人的登記、warrant 的登記、撤銷後簽、撤銷日期早於簽章、未來時間、假說之前、偽造簽章、
偽造的登記、簽後被改、簽章搬到另一筆、沒有設定 authority、非人類登記、一把金鑰兩個人、撤銷的金鑰再登記、
個人金鑰當 authority、登記被改或刪、繞過 trigger 改人名。

剩下的風險:authority 的持有者可以登記任何人;個人金鑰被本人濫用;
warrant gate 的職責分離(執行者、假說作者不能授權)還沒套用(SPEC-ISSUE-018)。

## 4. 盲測的輸入凍結與環境漂移

先證明漏洞(`evidence/blind_freezing_before.log`:19 個測試在 58c68be 全部失敗):
- runner 只比對生成端套件的雜湊,**沒有比對證據檔**:凍結後改過的證據檔照樣被執行。
- 套件先算雜湊,之後再從磁碟讀一次來解析:中間被換掉的檔案會被執行。
- 輸出裡的環境雜湊是呼叫者給的字串;執行前後都沒有檢查環境。
- `verify` 沒有比對:工作區是否乾淨、端點本身、平台、`LAB_BRAIN_*` 設定、資料庫實際套用的 migration、摘要是量到的還是宣告的。
- 模型摘要只有宣告:同一個名稱換了模型,沒有人發現。

修正:
- runner 讀一次每個凍結的檔案、比對雜湊,再用**同一份位元組**解析;沒凍結的檔案 → 拒絕。
- runner 在第一個案例前檢查環境(有差異就不跑),最後一個案例後再檢查;差異寫進輸出,scorer 拒絕評分。
- 環境紀錄多了:乾淨與否、端點、平台、設定(秘密只記有設定)、實際套用的 migration、摘要來源
  (本機 Ollama 回報且相符,或只有宣告)。伺服器回報的摘要和宣告不同 → 拒絕。遠端端點不會被詢問。

剩下的風險:目前任何差異都算不同實驗(最嚴格);可不可以放寬、宣告的摘要可不可以用在驗收,要 Owner 決定(SPEC-ISSUE-019)。

## 8. 後續(2026-11-02):審查者發現的偽造授權讀取路徑

分支:`g0-authorization-read-path-closure`(起點 `f41758c`)。

先證明漏洞(`evidence/forged_authorization_read_path_before.log`,4 個測試中 3 個在 f41758c 失敗):
- 部署用的**服務角色**可以寫入一筆簽章是偽造的驗證授權,和一筆以它為依據的 SUPPORTS。SQL 接受(SQL 不能驗 Ed25519)。
- 這筆 SUPPORTS 會被 `admitted_for_subject` 讀出來。所有信念決定都讀這個函式:
  信念轉移的授權輸入、驗證迴圈的確認規則、確認結論被重複使用前的重新檢查。
- 也就是說:偽造的支持**會進入**正式的認識決定輸入。評估收集器會拒絕它,但收集器只負責評分。

修正:
- `admitted_for_subject`:篩檢後假說的 SUPPORTS,只有在驗證函式說「沒有問題」時才算。沒有給驗證函式 → 一律不算(fail closed)。
- 驗證函式 = 011s 的 SQL 規則(用現在的資料列)+ 授權簽章(用固定的 authority)。
- 研究服務與確認重新檢查,每一個做決定的讀取都帶驗證函式(結構測試逐一檢查)。
- 事件頁面:不能驗證的支持顯示「記錄為支持,但不計入」(中英文)。
- 合法的路(本人簽章)仍然算數;篩檢前的假說不受影響。

正式驗收的盲測(`evidence/blind_acceptance_before.log`:舊程式根本沒有「驗收」這個區別):
- `--purpose acceptance`:runner 前後都驗證過環境,**而且**評估者自己的驗證紀錄:同一個環境、沒有差異、
  工作區乾淨、模型摘要是伺服器量到的、有寫驗證者、雜湊正確。少一項就拒絕評分。
- 預設 `diagnostic`:照樣評分,但寫明「不是驗收結果」;環境沒驗證時也寫明。

剩下的風險:
- 握有服務角色的人仍可寫入 SQL 外框接受的任何資料列(包括信念事件)。產品依賴它們的地方會在讀取時重新推導與驗證;
  一般的邊界是 A12 的部署邊界(服務、migrator、Owner 分開角色)。
- 要讓 SQL 在寫入時就驗簽,需要資料庫擴充(例如 pgsodium),這是 Owner/部署決定(SPEC-ISSUE-018 第 4 點)。
- 驗收紀錄的驗證者 id 是宣告的,沒有簽章(SPEC-ISSUE-019 第 4 點)。

驗證結果:見本節最後更新。
